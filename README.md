# Semantic TextNavigator — MVP проверки договоров поставки

Локальное веб-приложение для специалиста по закупкам: загрузка нескольких `.txt`, распознавание договоров и связанных материалов, таблица сумм и сроков **на выбранную дату**, проверяемые цитаты с переходом к соответствующему абзацу.

**Статус:** работающий демонстрационный MVP. **Важно:** в архиве находятся **6 синтетических тестовых TXT**, созданных для отладки. Это **не** исходные шесть файлов заказчика из папки `documents`. Поэтому ответы для реальных STN-101/102/103 не подтверждены, пока не загружены оригиналы.

## Быстрый старт

Требуется **Python 3.10+**, браузер. Платный аккаунт, API-ключи, подключение к Интернету и `pip install` не нужны.

```bash
python server.py
```

Открыть `http://127.0.0.1:8000` (сервер слушает только localhost).

1. Выбрать сразу все шесть оригинальных `.txt` из папки `documents` (либо нажать «Загрузить пример» для синтетического набора).
2. Оставить дату проверки **10.03.2026** либо выбрать другую.
3. Нажать **«Проверить договоры»**.
4. Изучить таблицу, ответы на 4 вопроса, блок «Требует внимания».
5. Нажать на выделенную **сумму/срок** или **«Показать источник»** — страница перейдёт к точному абзацу загруженного файла.
6. По желанию нажать «Экспорт JSON».

Тесты:

```bash
python -m unittest discover -s tests -v
```

Зависимости: **только стандартная библиотека Python**. `engine.py` — расчёт, `server.py` — локальный HTTP API, `static/index.html` — интерфейс, `samples/` — демонстрационный набор, `tests/` — тесты.

## Пример работы (только синтетические данные)

- STN-101: исходная поставка 15.04.2026, **подписанное действующее** допсоглашение переносит её на **28.03.2026**, источник результата — абзац допсоглашения; более поздний неподписанный проект отображается отдельно.
- STN-102: сумма **750 000 ₽**; срок **25.03.2026**; письмо с предложением переноса не меняет срок.
- STN-103: сумма **«нет данных»**, срок **12.04.2026**.
- До 01.04.2026: STN-101 и STN-102; по обоим есть несогласованные предложения. **Это не ответы на реальное тестовое задание**, а проверка сценария.

## Краткая продуктовая записка (≤ 2 страниц)

**Пользователь:** закупщик, регулярно сверяющий актуальную стоимость и дату поставки в договорах, допсоглашениях и переписке. Главная задача — сократить чтение документов, сохранив возможность доказуемой проверки каждой цифры.

**5 вопросов заказчику перед развитием:**
1. Как выглядят реальные форматы договоров и изменения: единая форма, сканы, таблицы, реквизиты или свободный текст?
2. Чем достоверно подтверждается подпись обеих сторон (электронная подпись, КЭП, сканы подписей, метаданные ЭДО)?
3. Что делать при нескольких действующих допсоглашениях с пересекающимися пунктами либо конфликтом дат?
4. Какие уровни доступа нужны: юрлица, подразделения, отдельные договоры; кто может исправлять/подтверждать извлечение?
5. Какая допустимая доля ручной проверки и что критичнее — пропустить изменение или ошибочно применить его?

**Допущения:** контрольная дата по умолчанию 10.03.2026; документ идентифицируется по содержимому; номер договора представлен подобно `ABC-123`; стоимость написана цифрами рядом с рублевой валютой; срок — конкретная календарная дата рядом с указанием поставки; каждый значимый пункт находится в одной строке (иногда в следующей). Письма и проекты не меняют условия. Изменение применяется, только если обнаружена явная формулировка подписи **обеими сторонами** и дата вступления в силу **не позже даты проверки**. Если этих свидетельств недостаточно, результат помечается для ручной проверки. Обнаруженная подпись по текстовой фразе — **эвристика, не криптографическая проверка**.

**Две метрики:** (1) *точность действующих значений с подтверждающими ссылками* = число правильно установленных пар «сумма/срок + цитата» / число экспертно проверенных пар; (2) *экономия времени закупщика* = медианное время проверки пакета с прототипом против ручной проверки, при одинаковом эталонном наборе.

**Архитектура:** Browser `File.text()` → POST `/api/check` (тексты + дата проверки) → Python `engine.py`: классификация → поиск номера договора → связывание → извлечение сумм/дат с индексами абзацев → проверка подписей и вступления в силу → применяемые/предложенные изменения → JSON → таблица, 4 ответа и цитаты с переходом по индексам абзацев. Данные не сохраняются на диск сервером. Кнопка примера читает **синтетические** файлы, а пользовательский сценарий — реальные загруженные тексты.

**3 технических решения и компромиссы:**
1. **Детерминированные правила и regex вместо LLM:** бесплатно, быстро, воспроизводимо, можно проверить цитаты; минус — чувствительность к вариативности формулировок и сложным табличным пунктам. Выбранный подход достаточен для малого TXT-MVP, но не универсального юридического анализа.
2. **Явный статус изменений + дата начала действия:** только подписанное обеими сторонами, вступившее в силу допсоглашение изменяет показатель. Неоднозначное или конфликтующее изменение требует проверки; минус — подпись в TXT не может быть надёжно доказана без данных ЭДО.
3. **Привязка к исходному абзацу и хранение дословной цитаты:** позволяет проверить вывод без доверия к алгоритму; минус — перенос строки в необычных TXT может разделить смысловое условие, а распознавание длинных многострочных пунктов ограничено.

**100 000 документов + права:** пакетная асинхронная обработка с очередью, объектное хранилище оригиналов, СУБД с версиями, индекс по договору и связи документов, поиск по тексту, механизм пересчёта при поступлении изменения, устойчивые идентификаторы/ссылки на исходные фрагменты; аутентификация через SSO, RBAC/ABAC вплоть до документа, разграничение на этапах выдачи, поиска и вычисления, аудит обращений, хранение событий проверки и контроль персональных данных. Текущий localhost-сервер, без хранения и авторизации, для такого объёма **не подходит**.

**Следующие 3 улучшения (приоритет):**
1. Валидировать и уточнить правила **по шести оригинальным документам**; добавить эталонные ожидаемые ответы и тесты регрессии на каждом условии/статусе.
2. Надёжная модель документов и событий: подписи и дата ЭДО, разрешение нескольких поправок по пунктам, история версий, объяснение конфликтов.
3. Извлечение с резервным локальным/доступным LLM и human-in-the-loop для нетипового языка, с обязательными цитатами и контролем ошибочных ответов.

## Краткий отчёт о вайбкодинге

- **Инструмент:** ChatGPT (GPT-6) для генерации кода, проектирования правил, подготовки тестов и README; исполнение и проверки — локальный Python.
- **Примеры запросов к ИИ (передают содержание задачи, не буквальная история чата):**
  1. «Сделай минимальный локальный Python-сервер и интерфейс, загружающий несколько TXT и показывающий значения с ссылками на точные абзацы».
  2. «Спроектируй модель применения изменений: только подписанное двумя сторонами соглашение, действующее на заданную дату; письмо и проект отдельно».
  3. «Проверь отсутствие суммы, подмену числа в тексте, неподписанный и будущий документ, конфликт изменений, точные цитаты».
- **Обнаруженная ошибка и исправление:** в первом проходе дата вступления допсоглашения сохранялась в ISO-виде `2026-03-05`, но проверка повторно распознавала лишь русскую словесную дату или `ДД.ММ.ГГГГ`. Поэтому действующее соглашение ошибочно не применялось. Добавлен разбор ISO-даты; исправление подтверждено тестом на применение действующего соглашения и тестом на будущую дату.
- **Проверки:** автоматические юнит-тесты (`python -m unittest discover -s tests -v`); ручная проверка результата на синтетическом пакете; отдельно нужно повторить проверку на оригинальных файлах заказчика.
- **Фактическое время:** точное время непрерывной работы инструментов не измерялось; при необходимости замерять следующую итерацию по таймеру. Не выдаём оценку за достоверно измеренные часы.
- **Что осталось:** запуск на 6 исходных TXT заказчика и сверка ответов с эталоном; улучшение распознавания вариативных документов; проверка UX в браузере интервьюера; реальное подтверждение подписей/даты через ЭДО. Это не промышленная система.

## Ограничения и безопасность

- TXT предполагается в UTF-8 (браузерное `File.text()`); старые Windows-1251-файлы необходимо преобразовать в UTF-8.
- Нераспознанные или неоднозначные даты и суммы требуют ручной проверки; формат периодов «через 20 рабочих дней» пока не поддерживается.
- Нельзя считать подписи доказанными только по текстовой строке. Ситуации с частичными изменениями пунктов, несколькими взаимно исключающими формулировками и сложной структурой требуют эксперта.
- Пользовательский ввод передаётся локальному серверу и не отправляется во внешние LLM; сервер не выполняет запись текстов, но результаты остаются в памяти браузера до перезагрузки страницы.
- Лимит API: 100 файлов, 5 МБ на один запрос. Без пользователей, БД, OCR, DOCX/PDF, внешнего доступа и произвольного чата — в соответствии с MVP.
